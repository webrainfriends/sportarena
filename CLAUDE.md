# Working agreements for AI assistants

- **Never commit or push to `main`.** Every change goes on a new branch (`feat/…`, `fix/…`, `chore/…`, `docs/…`) cut from the latest `origin/main`, and is delivered as a pull request into `main`.
- Open the PR automatically when the work is done, using `.github/pull_request_template.md`. Do **not** merge it — the maintainer merges manually and triggers builds.
- One concern per PR. Conventional Commit messages (`feat(scope): …`), clear body explaining the why.
- Run `npm test` (needs Postgres; see README) before pushing. Never commit `.env` or secrets.
- Features are added as capabilities in `apps/api/src/capabilities/*` (one definition → REST + OpenAPI + MCP). Personal identification data must use field-level encryption (`src/crypto.js`) and be audit-logged when decrypted.
- **Never ask the maintainer to log in to EC2 or run commands on a server.** Do server work through GitHub Actions (the runner SSHes in with the repo secrets) and read the results yourself via the GitHub API (list runs, get job logs; start a run with a workflow dispatch). If a workflow doesn't give enough visibility, add diagnostics to it in a PR instead of asking for manual steps. Only ask the maintainer for what only they can do: secrets, IAM/KMS permissions, security-group rules, and merging.
- **No dummy or hard-coded demo data.** Build real, usable modules: don't add seed rows, sample records or fake fixtures for new features, and don't hard-code example values into the UI. Tests create their own data; empty states and real forms are the default experience.
- **Data is never deleted — every design or code change must keep all existing data.** Migrations are additive and backwards-compatible (add columns/tables; never `DROP`/`TRUNCATE`/rewrite or narrow existing data, and backfill when you change a meaning). Deploys, seeds, scripts and CI must never reset, recreate or wipe the production database or its volume. Prefer soft deletes (status/`archived_at`/`left`) over `DELETE`, and don't add `ON DELETE CASCADE` to user data. Only the throwaway test database may be dropped. If a change seems to need data removal, stop and ask the maintainer first.
- **Use the right control, never free text where a control fits.** Dates and date ranges use the calendar picker, times a time picker, sports/venues/people/teams a search-and-pick control (multi-select when several can apply), fixed choices chips or a switch, money a currency amount field, numbers a stepper. Only genuinely free-form content (a name, a message, notes) is a text box. Think about what the user is really choosing and offer the smartest control for it (e.g. suggest venues that actually have courts for the chosen sports).
- **No overlapping features: one feature, one place.** Before building anything, search the app and API for a screen or capability that already does the same job, and extend it instead of adding a parallel one. Never add a second console, tab, form or capability for something that exists (the event console is the single home for running an event: teams, people, boards, games, venue, business, results). When two things turn out to overlap, merge them into one, move the data and entry points across without losing any data, and remove the duplicate route, button and code. Say in the PR what was merged.
- **Every feature ships on iOS, iPadOS, Android and web, API-first, MCP-enabled and security-compliant.** One React Native codebase (`apps/app`) must work on all four: no web-only or native-only APIs without a fallback, touch targets of at least 44pt, accessible labels, layouts that adapt from phone to tablet to desktop. Logic lives in an API capability (`apps/api/src/capabilities/*`) so REST, OpenAPI and MCP share it; the UI only calls the API. Authorization, validation, encryption of personal data and audit logging are enforced on the server, never only in the UI. Verify with `expo export` for web, iOS and Android before delivering.
- **Every feature works on iOS, iPadOS, Android and web, and the UX is designed for each.** The app is one Expo / React Native codebase, so build with the shared components and cross-platform primitives only (no web-only APIs such as `window`/`document` without a `Platform` branch; use `Share` natively and a download on web, etc.). Layouts must work at phone, tablet and desktop widths with touch-sized targets and accessibility labels. Verify the web build at phone and tablet viewports and say plainly in the PR what could not be run on a native device.
- **API first, MCP enabled, security compliant.** Every feature starts as a capability (REST + OpenAPI + MCP from one definition) and the UI only calls it. Enforce ownership, guardian/youth consent and live revocation inside the capability, encrypt personal free text (`*_enc`), audit sensitive reads and exports, and return `404` rather than leaking existence. Think like an elite athlete (a Grand Slam champion or Olympic medallist): pick from real catalogues and the athlete's own data, pre-fill what the platform already knows, and offer quick-picks, so typing is the exception.
- **Show the UX and get the maintainer's confirmation before the first commit of a feature.** Render the real screens (web build at phone, tablet and desktop widths, plus a design preview of anything that cannot be run), show them, and wait for approval before committing.
- **Close an issue only at 100%.** Review the work against every requirement and acceptance criterion with evidence (commands run, results, PR); if anything is short, keep building and re-review. Close the issue on GitHub only when everything is met and the change is on the delivery branch; otherwise leave it open with the exact blocker. Never merge or deploy without separate authorization.
- **Platform admin is exactly two accounts, and its features are invisible to everyone else.** Only the emails in `PLATFORM_ADMIN_EMAILS` (`rraja.edge@gmail.com`, `rrajas1978@icloud.com`) may hold `admin` / `platform_admin`; anyone else loses those labels at start-up and at sign-in (account and data are kept). Platform-admin-only features (e.g. the commercial console) enforce it on the server with `mustBePlatformAdmin`, are hidden in the app for every other role, and the "Add or remove roles" sheet and every public profile/roster never show or change `admin` / `platform_admin`.
- **Every sport, not just the popular ones.** A feature that touches scoring, results, rules, events or athlete data must work for every sport the catalogue lists. Give each family its own native model (a cricket innings is not a football half is not a tennis game is not a heat), label any generic fallback as such, and never leave a sport on a silent default. State in the PR which sports are covered natively, which use a labelled fallback, and which are still a gap. A test should walk the whole catalogue.
- **UX is shown to the maintainer as PNG images only, in the app's own theme.** Send screenshots (phone, tablet, desktop) as `.png`, never HTML: HTML previews do not display on the maintainer's iPad. Use the existing theme tokens in `apps/app/src/theme.js` (the Dusk palette, light and dark), never new colours. Lists that can grow (events, venues, competitions, teams) use a searchable dropdown multi-select (`MultiMenuField`, `MenuField`), not a row of chips.
- **Every feature ships in the 11 language packs plus the existing ones.** Tamil (`ta`), Telugu (`te`), Malayalam (`ml`), Marathi (`mr`), Kannada (`kn`), Bengali (`bn`), Odia (`or`), Hindi (`hi`), Sinhala (`si`), Urdu (`ur`, right-to-left) and Bahasa Indonesia (`id`), alongside English. Any new or changed user-facing string (screen text, titles, placeholders, accessibility labels, empty states, error and notification text) is added as a key in `apps/app/src/i18n/en.js` and in every language file there, read through `t()`; never hard-code English in a screen. Layouts must work right-to-left (use start/end, not left/right), search and matching must handle the native scripts, and PDFs/documents must not garble them. Machine-drafted text stays `reviewed: false` until a native speaker signs it off. `test/i18n-catalogues.test.js` must pass, and the PR states which new text is translated and which falls back to English.
