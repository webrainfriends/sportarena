# Sponsorship ROI & portfolio intelligence (#519)

The layer on top of the sponsorship lifecycle (agreements, dues, awards, renewals, disputes, reports) and the public event pages (#501):
**discover → evaluate → contract → activate inventory → track deliverables → measure real exposure → resolve issues → report → renew.**
It reads the canonical records; it does not copy them. Finance truth stays in `sponsorship_obligations` / `sponsorship_payments` and is read through
`list_sponsorship_obligations`; nothing here is a second ledger, console or report engine.

## Assessment: sponsor decision → existing fact → measurable exposure → gap → extension

| Sponsor decision | Existing fact (reused) | Measurable exposure / deliverable | Gap | Extension (this issue) |
|---|---|---|---|---|
| What can I buy, is it free? | `endorsement` lines carry free-text rights/exclusivity; #501 placements are one slot per event | none | no governed inventory, no capacity or category-exclusivity, placements not tied to a contract | `sponsor_inventory_units` + `sponsor_inventory_bookings`; a placement of an inventory-governed slot needs a live booking |
| Did they deliver? | dated money/goods/endorsement dues with receipt/review; media-licence deliverables (`mr_deliverables`: naming mention, overlay, content piece, signage) with delivered/verified | endorsement posts, licence deliverables | appearances, content, hospitality, rewards had no owner, evidence, reviewer or exception path | `sponsorship_deliverables` (+ evidence, exceptions, log): accepted only by the other side with evidence; deliverable health counts both sources once |
| What exposure did I get? | `placement_daily_counts` (served, clicks), `spectator_follows`, media-rights `mr_measurements` (named-source reach per licence deliverable) | counts above | no published definitions, no non-broadcast provider figures (attendance, tickets, hospitality, page views), no gaps shown, no dedupe rule, nothing joined per agreement | metric catalogue, `sponsor_exposure_signals` (non-broadcast only), `get_sponsorship_exposure` reading all of it |
| What is it worth? | goods/endorsement `estimate_cents` (labelled estimates) | none | no customer-owned valuation or ROI | versioned `sponsor_valuation_*`; every output labelled an estimate |
| How is the portfolio doing? | #305 reports (ageing, funnel, outcomes, fulfilment, renewals), #292 beneficiary portfolio | per-report | no per-brand view joining money, deliverables, exposure, disputes, renewals; no safe comparison | `get_sponsorship_portfolio_intelligence`, `compare_sponsorship_campaigns` |
| Should I renew? | #299 renewal assessment / proposal | all of the above | no factual pack | `get_sponsorship_renewal_pack` (facts only; existing renewal capabilities do the renewing) |
| Prove it | #305 exports (live, not frozen) | snapshot | nothing immutable | `sponsor_roi_reports` (hash, DB triggers refuse UPDATE/DELETE) |

## What was merged, not duplicated
- **Broadcast reach** stays in media rights (`record_media_measurement` → `mr_measurements`, named source and reference). The ROI layer *reads* measurements recorded against licence deliverables that name the agreement (`broadcast_views`, `broadcast_impressions`, `broadcast_watch_minutes`, highest-reported `broadcast_unique_viewers` / `broadcast_peak_concurrent`); there is no second place to type stream views, overlay impressions or clip views, and the ROI ledger rejects those metrics.
- **Licence deliverables** stay in media rights (`mr_deliverables`, partner delivers, organiser verifies). They count in deliverable health (verified = accepted, delivered = awaiting review, missed/late = overdue). `sponsorship_deliverables` is only for agreement deliverables that are *not* delivered through a media licence (appearances, content, hospitality, rewards, activations); dated social posts remain endorsement dues.
- **Inventory for an event** is managed in the **event console → Business** (the event's single home for sponsors and vendors) using the shared inventory component; the ROI screen points there for events and manages team and athlete inventory itself (they have no console).
- **Public placements** (#501) are not re-implemented: `save_sponsor_placement` gains a booking gate and `event_sponsor_placements.booking_id`.
- **Money** is read from the dues and payments; **renewals** stay in `assess_/propose_sponsorship_renewal`; **reports** are a separate immutable kind with the same export engine as #305.

## Rules
- **Inventory is contract-linked.** A booking needs an *active, accepted* agreement with the same event/team/athlete, inside the agreement term and the unit's availability. The owner (event organiser / team owner / adult athlete) books it; sponsors cannot book for themselves. The unit row is locked while capacity and category-exclusivity are checked, so parallel bookings cannot double-sell (tested: 5 racers, 1 seat → exactly 1 booking). Releasing a booking ends the public placement it backs. A young athlete's sponsorship is not sold as inventory.
- **Public, broadcast and media placements link to authorised inventory.** Units of kind title partner / scorecard / leaderboard / event page sell the #501 slot of the same name: once an event defines a unit for a slot, `save_sponsor_placement` requires a live booking of that unit by that sponsorship (409 `inventory_required`). Once an event defines overlay / replay / social / signage-type units, a media-licence deliverable that names a sponsorship (`save_media_deliverable`) must be backed by that sponsorship's live booking of a matching unit (graphic overlay → livestream overlay; naming mention → overlay, replay or title partner; content piece → replay, social or content; signage → kit, associate or title partner), and is stored with `booking_id`; delivering it after the booking was released is refused (409 `booking_released`). Events with no inventory defined behave exactly as before (backwards compatible). Highlight clips carry no sponsor field in media rights, so they are covered through the media-licence deliverable that names the sponsor.
- **Deliverables never complete by themselves.** Owner side submits evidence (https link and/or up to 3 encrypted files); the **other** side accepts or sends back (note required). Acceptance needs evidence meeting the requirement and records reviewer and time. The end of an event, a due date or a term changes nothing (overdue is derived). Exceptions (postpone / waive) are requests the other side decides; a waiver is counted as *excepted*, never *accepted* and never *missed*.
- **Exposure is measured or absent.** `platform_measured`: placement impressions and clicks (#501), distinct followers (a point-in-time count). `provider_reported`: stream views, overlay impressions, clip views, page views, attendance, tickets scanned, hospitality guests, entered by the beneficiary with provider name and a checkable reference. One live value per agreement, metric and day whatever the source, so two sources are never added; corrections supersede and keep history. An expected metric with no data is listed as **missing**, never zero. `GET /sponsorship-metric-definitions` publishes definitions, bases and dedupe rules; the same definitions are embedded in every report. Never measured: social reach, unique audience, brand awareness/sentiment/sales lift, AVE.
- **No fake AVE/ROI.** A monetary estimate exists only from a valuation version the brand wrote (rate per unit or per 1,000 for chosen *measured* metrics, currency, rationale). Versions are immutable (trigger); the estimate shows measured value, basis, rate and model version, is labelled "ESTIMATE — assumption-based, not a measured fact", and a return-on-spend ratio appears only with confirmed spend in the same currency. Beneficiaries never see the brand's assumptions.
- **Portfolio reconciles, never duplicates.** Money totals come from `list_sponsorship_obligations` (the same handler the agreement screens use). Exposure totals cover the rows returned and never add follower counts across agreements. Youth athletes are masked.
- **Comparison.** One explicit period; a metric is compared only when measured, period-based, same basis and present for every selected agreement; the rest are listed as not comparable with the agreements that lack them. Spend compares only within one currency. Values are also per active day (partial windows flagged). The result keeps the order given: no ranking, no score.
- **Renewal pack.** Facts and plain sentences generated from agreement, dues, deliverables, exposure, disputes and (only if the beneficiary shares them, through `get_sponsorship_performance`, so the athlete's consent and youth rules apply) outcomes. It proposes nothing; renewing stays in `assess_sponsorship_renewal` / `propose_sponsorship_renewal`. Any narrative (human or AI) must stay within `facts`.
- **Reports are immutable.** `issue_sponsorship_roi_report` freezes agreements, finance, deliverables with evidence links, exposure, definitions, gaps and the valuation note; stores a SHA-256 of the canonical JSON; DB triggers refuse UPDATE/DELETE. `get_` verifies the hash on every read; exports (CSV/XLSX/branded PDF) are built from the stored snapshot. Sponsor reports need `roi` on the brand; a recipient report covers one agreement, carries no valuation and no other agreements. Access is checked live and answers 404 otherwise.
- **Privacy.** No recipient health, finance or contact data appears anywhere; deliverable files are encrypted at rest, shown only to the two sides and audit-logged on read; notices carry no figures.

## Permissions (`SPONSOR_ACTIONS`)
`roi` = manager, finance, approver, auditor (read dashboards, exposure, packs, reports; issue sponsor reports). `valuation` = manager, finance (write assumptions). Deliverable actions on the sponsor side use the existing `evaluate` action. Department-scoped members only see their department's agreements. REST, OpenAPI and MCP share each definition (`apps/api/test/sponsorship-roi.test.js` asserts parity and that MCP enforces the same denial).

## Capabilities
Inventory: `create_sponsor_inventory_unit`, `update_sponsor_inventory_unit`, `list_sponsor_inventory`, `book_sponsor_inventory`, `release_sponsor_inventory_booking`, `list_sponsorship_inventory_bookings`.
Deliverables: `create_sponsorship_deliverable`, `list_sponsorship_deliverables`, `submit_deliverable_evidence`, `get_deliverable_evidence_file`, `review_sponsorship_deliverable`, `request_deliverable_exception`, `decide_deliverable_exception`, `cancel_sponsorship_deliverable`.
Measurement and valuation: `list_sponsorship_metric_definitions`, `record_exposure_signal` (non-broadcast only), `correct_exposure_signal`, `get_sponsorship_exposure`, `create_valuation_model`, `add_valuation_version`, `list_valuation_models`, `get_sponsorship_valuation`.
Intelligence: `get_sponsorship_portfolio_intelligence`, `compare_sponsorship_campaigns`, `get_sponsorship_renewal_pack`, `issue_sponsorship_roi_report`, `list_sponsorship_roi_reports`, `get_sponsorship_roi_report`, `export_sponsorship_roi_report`. Extended: `save_sponsor_placement` (`booking_id`, booking gate), `save_media_deliverable` / `set_media_deliverable_status` (booking gate, `booking_id`).

## Schema (migration `123_sponsorship_roi.sql`, additive)
`sponsor_inventory_units`, `sponsor_inventory_bookings`, `event_sponsor_placements.booking_id` (nullable), `mr_deliverables.booking_id` (nullable), `sponsorship_deliverables`, `_evidence`, `_exceptions`, `_log`, `sponsor_exposure_signals`, `sponsor_valuation_models`, `sponsor_valuation_versions`, `sponsor_roi_reports`. No existing column is dropped or narrowed, no row is deleted, no seed data. Soft state only (archived, released, superseded, cancelled).
**Rollback:** deploy the previous code; the new tables and the nullable column are simply unused. **Dependency order:** needs ≤ 122 (agreements 042, renewals 099, disputes 101, public spectator 118).

## UI
`SponsorRoi` in `apps/app/src/screens/sponsor-roi.js`, opened from **Sponsors → Funding programs → ROI & exposure**; event inventory is also in **Event console → Business → Sponsor inventory** (same component). It extends the Sponsors area; it does not replace the beneficiary portfolio (#292) or the #305 reports, which stay the per-beneficiary and per-ledger views. Brand side: Portfolio (drill into an agreement: Exposure, Deliverables, Estimate, Renewal pack, Inventory), Compare, Valuation, Reports. Beneficiary side: Inventory (team and athlete; events point to the console), Sponsorships (deliverables, provider figures, renewal pack), Reports. Controls follow the app rules: dates and periods use the calendar, kinds/categories/metrics are chips, capacity is a stepper, exclusivity a switch, rates a currency amount, brands/events/teams/agreements a search-and-pick; free text is only names, notes, source references and rationale. Provider figures are typed numbers (counts from a report) with the provider and a reference.

## Sports
Inventory, deliverables, exposure and reports are sport-agnostic: they attach to events, teams and athletes of any catalogue sport and do not score or rank anything by sport, so there is no per-sport model to fall back from (stated plainly; no sport is on a silent default).

## Limits (stated plainly)
- No streaming/broadcast provider is integrated: broadcast reach exists only as the named-source figures recorded in media rights, and non-broadcast provider figures only as beneficiary-entered, provider-labelled records. Platform-measured counts are limited to the #501 public pages and followers.
- Impressions count public responses, not unique people; unique reach is not measured.
- An agreement's free-text endorsement exclusivity terms are not parsed; exclusivity is enforced on the inventory unit's category rule.
- Portfolio exposure totals cover the rows returned; finance totals cover all matches.
- AI-drafted renewal narratives are not wired in; the pack exposes `facts` for any drafting.
- Native iOS, iPadOS and Android builds were not run in this environment: the shared React Native code compiles for web and was verified in a browser at phone, tablet and desktop widths.
